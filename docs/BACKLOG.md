- 修改文件時只動指定的那一條，其餘條目不要更動。

## 設計總則（手機版定位）
- 手機版定位：快速記錄 + 完整閱讀、判斷現狀。
- 結構性設定（任務階層/子任務、依賴關聯、重複規則等）交由桌面版建立，手機版不提供建立入口。
- 手機版可「唯讀顯示」這些結構（如子任務清單、依賴狀態），但不提供編輯/新增。
- 輔助層（節律/指標/軌跡/收成）在手機版只做精簡版，管理功能留在桌面版。

### 1. 重複任務生成搬到資料庫層

- **影響範圍**：桌面版 / 手機版 / Supabase

- **為什麼留到之後**：搬到 Supabase 是正解（兩端共用一份邏輯），但牽涉資料庫自動化、日期計算重寫、且要同時修一個既有的「防重複比對只看標題」弱點，屬進階任務。

### 2. 換日時間（dailyResetHour）跨裝置同步

- **動工前要先確認**：

### 4. 失敗提示 toast 抽成共用元件
- **優先級**：中（原為低；階段 1.5-B B-4b 又在同一份 inline 程式碼上加了 kind 樣式分支，三頁重複度更高，優先度提高）
- **影響範圍**：手機版
- **狀態**：暫緩（維護債）
- **描述**：目前 Focus / Tasks / TaskDetail 各有一份幾乎相同的 toast inline 程式碼（重複三份）。階段 1.5-B B-4b 為了讓「錯誤」與「中性提示」（新增的 `actionNotice`）呈現不同配色，各頁 `Toast` 又各自加了一份 `kind: 'error' | 'notice'` 樣式分支，三份程式碼因此更相似、重複度更高。
- **為什麼留到之後**：B-4b 明確要求「不要把三份 toast 抽成共用元件、本階段維持現狀」，故沿用既有重複寫法；抽成共用元件屬獨立重構，留待後續階段評估。
- **動工前要先確認**：抽取時需同時支援 error/notice 兩種樣式分支，並確認三頁呼叫端（Focus.tsx / Tasks.tsx / TaskDetail.tsx）的 props 介面一致後再合併。

### 5.〔桌面版〕settings.json 混存登入憑證（安全問題）
- **優先級**：高
- **影響範圍**：桌面版
- **狀態**：暫緩（手機版階段 2 完成後回頭處理）
- **描述**：桌面版 settings.json 把登入憑證（JWT token）與一般偏好設定混存在同一個純文字檔，任何能讀到該資料夾的程式都能取得憑證。
- **為什麼留到之後**：這是桌面版的問題、不是手機版，且現在手上多條線同時進行，不宜插隊。但嚴重度高於一般體驗項目，不可被遺忘。
- **動工前要先確認**：把 authSession 從純文字 settings.json 移到 Electron safeStorage / OS keychain。此為桌面版任務，需用桌面版 Code。

### 7. 列表滑動刪除（手勢體驗升級）
- **優先級**：低
- **影響範圍**：手機版
- **狀態**：待實作
- **描述**：列表目前用「長按」刪除任務。未來可加入「滑動刪除」手勢提升順手度。另外，目前長按刪除沒有震動或視覺回饋，未來做手勢體驗時可一併加入 haptic（震動）與列高亮提示。
- **為什麼留到之後**：滑動手勢細節多（觸發距離、放手回彈、與捲動衝突），易誤觸，值得單獨花一次做好手感，不與其他功能混做。
- **動工前要先確認**：與既有捲動行為不衝突；滑動一半放手要能回彈；保留長按或詳情頁刪除作為備援入口。

### 8. 軟刪除後 task_dependencies 殘留孤兒依賴
- **優先級**：低
- **影響範圍**：手機版 / 共用（Supabase 資料）
- **狀態**：暫緩（資料清理議題）
- **描述**：軟刪除任務時，指向它或由它指出的 task_dependencies 依賴列仍留在資料庫，成為指向已隱藏任務的孤兒記錄。
- **為什麼留到之後**：目前所有查詢端都會過濾掉已刪任務，孤兒依賴不會造成顯示錯誤；且保留依賴讓「復原任務」時依賴關係能自動還原，現階段反而是好事。純屬資料乾淨度議題，不影響使用。
- **動工前要先確認**：清理策略要與「復原」並存——若硬清掉依賴，復原後關係就回不來了。需決定是否改用軟刪除依賴、或復原時一併重建。

### 9. 手機完成的更替紀錄無法在桌面自動復原
- **優先級**：低
- **影響範圍**：手機版 / 桌面版
- **狀態**：已知限制，接受
- **描述**：手機記錄完成時 `maintenance_events.generated_next_task_id` 寫入 `null`（手機不產生任務），桌面復原功能靠此欄回收下一輪任務，因此復原手機完成的那一輪時，桌面產生的新任務可能留下需手動刪除。
- **為什麼留到之後**：手機端本來就被要求「不得產生 tasks」，`generated_next_task_id` 必然是 `null`，這是設計上的必然結果而非疏漏；影響僅限於「桌面手動復原手機完成的那一輪」這個少見操作，接受現狀即可。
- **動工前要先確認**：若要處理，需在桌面復原邏輯加一條「`generated_next_task_id` 為 null 時，改用 `maintenance_item_id` + `event_date` 回頭找同一輪產生的任務」的備援查找，屬桌面版任務。

### 10. 日期演算法在負時區會差一天
- **優先級**：低
- **影響範圍**：手機版 / 桌面版
- **狀態**：暫緩，僅在使用者長期跨到負時區時才需處理
- **描述**：`calcNextDueAt` 以 UTC 午夜解析日期字串、卻用本地時間讀寫日，在美洲等負偏移時區會算出差一天的結果。桌面同一段程式碼行為相同，兩端一致故不會造成增生。
- **為什麼留到之後**：目前使用情境以 Asia/Taipei（UTC+8，正偏移）為主，不受影響；且這是桌面既有演算法的既定行為，手機刻意逐字元鏡射桌面（見 `docs/MOBILE_STATUS.md` B-2 段落），並非手機獨有的新問題，貿然修正反而會讓兩端不一致。
- **動工前要先確認**：修正需兩端同時處理（否則兩端算出不同的 next_due_at 會互相覆蓋），且要先確認是否真的有使用者在負偏移時區使用本 App。

### 11. 提示語氣只有一種中性樣式
- **優先級**：低
- **影響範圍**：手機版
- **狀態**：暫緩，需第三種提示樣式時再處理
- **描述**：「已完成並推進週期」與「已標記完成但未推進週期」目前共用同一種綠色提示，使用者只能靠讀文字分辨。
- **為什麼留到之後**：階段 1.5-B B-4b 明確要求「只新增一個中性提示狀態、不要大範圍重構」，故兩則訊息暫時共用同一種樣式；細分語氣需要新增第三種 toast 樣式（例如中性灰 vs 正向綠），屬於下一輪 UI 調整，不在本階段範圍內。
- **動工前要先確認**：決定第三種樣式的色彩（沿用專案既有色票，避免新增紅色以外的警示感），並確認 `useTasks` 是否需要拆出比 `actionNotice` 更細的狀態，或改用一個帶 `kind` 的物件而非純字串。

### 12. 更替任務葉子標記依賴 task_type 欄位
- **優先級**：中
- **影響範圍**：手機版 / 共用
- **狀態**：待確認
- **描述**：標記與刪除防護皆以 `task_type === 'maintenance'` 判斷，若雲端該欄未正確帶值（例如舊資料），標記與防護會同時失效。
- **為什麼留到之後**：目前無法確認雲端既有資料是否都正確帶有 `task_type`，需要先查證再決定是否要加防護。
- **動工前要先確認**：雲端 `tasks` 是否存在 `maintenance_item_id` 有值但 `task_type` 為空的資料。
